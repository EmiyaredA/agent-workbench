# 维护记录：write-notes 与 mini-trellis 的融合建议

状态：2026-11-24 固定版本调研。后续实现已完成四视图、明确关联和可选 operationId 重试；外部变更送审、决策编辑与封存仍未实现。文末探针保留调研当时的结果，不代表更新后的代码仍有相同 record 行为。

结论：以 write-notes 保存重要决定的来由，以 mini-trellis 的 journal 思路记录实际迭代和交接，用明确链接关联两者。文件仍是唯一正文来源；一次普通维护不必产生两份文档。

## 三块产品职责

| 区域 | 回答的问题 | 边界 |
| --- | --- | --- |
| 约束 | 当前要遵循哪些规则？ | 项目文件按目录展示；全局偏好独立。历史决定不自动成为规则。 |
| 提案 | 哪些约束变化需要用户审阅？ | 只负责约束变更，项目与全局同样处理；不把工程方案的实施状态混入审核状态。 |
| 维护记录 | 项目怎样迭代，为什么这样改？ | 实际改动、验证、未决问题和决策取舍；可记录一次约束审核的结果，但不是审核入口的替代。 |

用户这轮描述还包含“外部直接改文件后进行审阅”。当前实现只支持已提交候选的准确差异审核，以及原文变化时阻止已有候选写入；没有针对所有文件的已审基线或外部改动自动入队。两者不能等同。

## 可取用的互补能力

| 来源 | 值得吸收 | 在工作台中的用法 |
| --- | --- | --- |
| write-notes | Problem、Decision、Alternatives considered、Consequences | 重要决定保存背景、真实考虑过的备选、收益与代价，不只写修改摘要。 |
| write-notes | proposed／implemented／rejected／archived 与六类主题 | 展示方案稿、实际落地、否决与历史；类别用于筛选，避免把状态当日期。 |
| write-notes | 同主题优先原地维护、理由翻转另开并互链 | 同一个决定可经历多次维护，不为每次小修生成一篇重复笔记。 |
| write-notes | 格式校验、归档封存和相对链接 | 值得逐步接入的校验；归档只在确有需要时启用，不能宣称已有完整封存支持。 |
| mini-trellis | change／test／next-step、topic 与提交证据 | 每次有交接价值的迭代记录实际改动、验证和后续，链接到已有决策或约束。 |
| mini-trellis | 带幂等标识的记录与失败后收敛 | 同一操作的重试不重复写日志；两次真实维护即使摘要相同，也应能分别留下记录。 |
| mini-trellis | 按需 recall／read、来源指纹及过期引用提示 | Agent 先定位相关历史，再展开正文；来源已改变时重新读取，不把旧摘录当现状。 |
| mini-trellis | 当前规则、研究、日志与被替代内容的区分 | 看板关联来源，只有提炼出的约束候选通过审核后才进入有效规则。 |

这些是建议取用的能力，不表示整套上游已接入。mini-trellis 的直接 remember 写规则流程不符合本项目逐次审阅边界，应保持候选化；不引入自动提交或常驻采集。

## 维护记录如何呈现

按用户后续确认，保留架构基线、演进时间线、避坑智库、决策清单四视图；时间线以月份、类别和记录类型筛选。迭代记录与工程决策有明确类型，可以在同一视图关联查看，不再只是两个互不相连的列表。

每条迭代展示日期、标题、实际结果、验证和相关文件。打开详情再看背景、后续、关联约束／审核、决策笔记和提交证据。没有证据的字段留空，不拼造提交号或验收结论。

有重要取舍时，维护一篇决策笔记；有后续修改时，让新迭代链接同一篇笔记。决策内容只保存一份，时间线引用它，不复制整篇正文。相同项目、相同日期或相似标题都不足以自动认定为同一次迭代。

例：

1. 11月20日，提出文件存储方案，决策笔记处于 proposed。
2. 11月23日，代码落地并完成指定验证，维护记录链接该笔记、相关文件与真实证据；笔记转 implemented。
3. 11月24日，修复恢复边界，增加一次维护事件，仍关联同一决定。
4. 若形成新的长期约束，另外进入提案区，用户审阅具体差异后再生效。

批准一条约束不代表某项工程实现已经完成；工程方案获认可也不等于已落地。维护事实可以由 Agent 留档，但不能顺带修改有效约束。

## 保持现有目录，不复制第二份正文

- 约束仍在 AGENTS.md 和 .agent-workbench/rules/。
- 日常迭代继续使用 docs/maintenance/YYYY-MM.md。
- 已有决策笔记继续从 .agents/notes/{状态}/{类别}/日期-主题.md 读取。
- 已有 mini-trellis journal 保留只读兼容；未证明有必要前，不迁移其日志或重写其索引。
- 关联优先使用现有 topic 字段与相对 Markdown 链接，先补结构化解析与跳转，不建立图数据库或第二个手工总索引。

索引可在内存按文件派生。新的 Node 写入接口应承担实际修改；Skill 只指导何时读取、记录、提议，不能代替验证与恢复逻辑。

## 合并时必须处理的差异

### 日期不是同一种时间

write-notes 文件名保存首次提出日，方案落地时不改这个日期；其看板也是从文件名提取日期。mini journal 记录一次实际活动的日期。未来时间线应以维护事件的发生日为准，并保留决策的首次提出日，不能用文件名或mtime伪造实施历史。

### 归档封存与替代标记

write-notes 将已落地笔记物理移入 archived，保留 Status: implemented，紧跟 Archived: YYYY-MM-DD，并登记SHA-256。不能把归档文件改成 Status: archived，也不能封存后再向它添加 superseded_by。

新的决定可链接历史快照；未封存的活动文档可使用 mini-trellis 的替代关系。关系读取需要区分对象，不能用一种状态字段覆盖全部记录。

归档脚本只提示活跃笔记中的入站链接，不会自动修复所有引用，更不扫描维护日志中的全部旧链接。移动笔记前要核对日志与正文链接；不能先写一条“归档成功”就声称关联均可用。

### 发现范围与按需读取

mini-trellis 默认发现器不保证发现 .agents/notes；它还有跨会话召回能力。不能直接调用全量 recall 就认为已经覆盖决策笔记。当前工作台的显式目录读取已能发现这些笔记，融合应延续这个边界，再接入相应的来源引用能力，不扩大到全部会话。

### 写入与重试

mini 日志写入器把追加、索引和可选提交作为可恢复操作处理，不以文本相同作为永久去重标准。工作台已有约束批准回执和日志幂等，但普通 record 每次分配新键，重复调用会产生两条记录。下一步应允许调用方为一次操作提供稳定幂等键，避免网络超时重试重复落盘，同时保留两次真实维护。

write-notes 的归档是文件移动、封存和新笔记互链等多个步骤。若以后提供归档按钮，应设计中断核对与重试，不能直接运行脚本后凭退出码笼统宣告全流程完成。

## 现有实现与缺口

| 能力 | 当前状态 |
| --- | --- |
| 按月维护记录、背景／结果／验证／后续 | 已有 |
| 决策四种生命周期与详情阅读 | 已有只读展示 |
| 约束批准与日志写入的幂等恢复 | 已有 |
| 普通record的调用方幂等键 | 已实现可选 operationId；跨进程与跨月重试核对 |
| 迭代事件和决策的结构化关联 | 已实现明确路径／相对 Markdown 链接关联及双向跳转 |
| 真正按关联文件筛出的“相关维护” | 没有；当前约束页取最近两条项目记录 |
| 决策创建、状态流转、格式检查及封存 | 没有完整写入流程；示例不代表已实现上游校验协议 |
| mini-trellis完整来源引用／过期证据提示 | 未接入该完整流程 |
| 外部直接编辑的自动送审与已审快照 | 没有；当前context读取的是磁盘现状 |

## 外部改动审阅需要单独补的一层

建议为登记约束保存最后审阅版本，首次登记应明确尚未建立审阅基线，不能默认为已经看过。项目与全局按同一规则核对。

在显式刷新／扫描动作中比较当前文件与基线，形成外部变更候选；不靠长期观察进程。只读接口仍保持只读，扫描生成候选通过独立写接口处理。批准时再次核对当前版本，避免审阅期间的新编辑被误接纳。

若外部已经写入，接受的动作是确认该版本并更新审阅记录，不必再覆盖一遍文件。拒绝应保留未审状态，或由用户另行审阅恢复差异，不静默撤销外部编辑。

工作台可明确区分已审与磁盘版本，但不能阻止同一用户的其他工具直接读取或改写磁盘文件。首选仍是由Skill先提交候选，审阅后再写正式约束。

## 建议实现顺序

1. 先校准三块职责及外部变更的审核语义，避免当前状态被误认为完整已审系统。
2. 先融合维护记录的最小链路：迭代事实 → 关联决定 → 验证／后续；统一展示和查询，不强制每次活动新建笔记。
3. 补普通记录的稳定幂等键、必要的笔记格式校验和来源有效性提示。
4. 确有历史替代需求时，再增加封存、引用检查及状态迁移；不首期堆入全套工具链。
