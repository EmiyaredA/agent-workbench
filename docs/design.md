# agent-workbench 整体设计

状态：2026-11-24 的设计基线。v0.1 已实现登记、约束阅读、提案审核、维护日志与 Skill 入口；具体使用和当前边界见 [README](../README.md)，验收见 [design-qa](../design-qa.md)。下文保留设计取舍，未来选项不代表全部已实现。

2026-11-25 补充启动与分发：源码可直接 `npm start`，首次按锁文件自动准备运行依赖（联网、跳过安装脚本、排除开发依赖）；本地构建的 `.tgz` 内置锁定版本依赖及许可，解压后仅需 Node.js 24+，运行 `node start.mjs` 即可离线使用。继续复用现有库，没有改写为零依赖实现；分发包尚未远端发布。开发验收仍先安装完整依赖。具体使用见[使用指南](usage.md)。

2026-11-25 用户进一步澄清：重点是每次约束迭代都有记录，不要求每次先人审。当前已增加直接修改并留档，与可选提案共用“变更记录”的时间线、清单与同页抽屉。`change` 按已读取的 baseHash 写入，保留前后正文、来由、来源及幂等标识，同步追加事实日志；recorded 与审核后的 applied 分开。下文“每次人审”属于初始设计取舍，不再是所有作用域的统一产品门槛；具体任务仍遵守其用户授权和项目约定。历史外部编辑没有快照时不推造差异。

当前目录固定为根 `AGENTS.md`、`.agent-workbench/rules/index.md` 与按需模块、`docs/maintenance/`。2026-11-25 按用户要求移除旧目录配置、自定义映射和 `.trellis/workspace` 自动读取；只读参考仍可逐文件登记。具体实现以[目录约定](directory-convention.md)为准；下文的旧目录兼容方案属于历史设计，不是现有能力。

维护记录的进一步融合建议见 [write-notes × mini-trellis 调研](research/maintenance-integration.md)，包含固定版本探针与当前缺口。同一决策集合的维护四视图、迭代关联与记录重试现已实现。2026-11-25 补充 Skill 决策写作／状态流转指引与 CLI 校验／归档；看板仍只读，外部变更自动送审未实现。

## 1. 选型：以 mini-trellis 的 core 与文档能力做底座

选择 mini-trellis 已分离的 **core 公共 API、现有 Markdown 发现、来源引用、文档替代关系与日志能力**作为底座。它比 CE 更接近“多个 Agent 共用项目文档和维护来由”，已有可直接调用的实现，避免重新开发同类文档和来源能力。固定版本和改选依据见 [mini-trellis 专项审查](research/mini-trellis.md)。

优先依赖 `mini-trellis-core` 的公开导出；确实需要修改时才维护有明确差异的小派生。不要 fork 整仓后继续携带全部宿主安装器，也不要默认运行它的直接写入技能。**全局约束管理、审核状态机和薄界面仍需要补上。** 本轮尚未搬入上游实现。

| 来源 | 首版取用 | 不带入核心的部分 |
| --- | --- | --- |
| mini-trellis | `discoverDocs`、项目根边界、来源引用及 `superseded_by`；兼容既有日志；按需读取选定会话来源 | 整套初始化／迁移／宿主安装器、默认遍历所有本机会话、确认观点即直接写入规则的原始技能 |
| Compound Engineering | 按条件读取规则；只保留值得复用的经验；更新、收窄、清理失效文档 | 完整工作流、多 Agent 编排、Bun 转换器、第二套规则包管理和远程分发 |
| ECC | 从明确纠正、重复偏好、已验证问题中产生候选；区分项目与全局；展示触发条件和来源 | 全量工具调用采集、常驻 observer、置信度自动生效、自动生成技能／命令／Agent |
| CloudCLI | 后续按需接入项目上下文与插件页生命周期 | 宿主会话、终端、模型 SDK、宿主数据库和插件子进程作为工作台必需依赖 |

更换这个看板不应迫使用户迁移项目文档。四个上游中，没有一个原样满足“多层文件约束 + 每次更新人审 + 可迁移维护日志 + 轻运行时”的完整组合。

## 2. 六项需求对应的最小能力

| 用户需求 | 设计 | 可验收结果 |
| --- | --- | --- |
| 项目 AGENTS.md | 原位读取和编辑，建议修改经过审核 | 可以看到当前原文、修改理由和精确 diff；批准后只改目标文件 |
| 全局 AGENTS.md | 个人全局文件单独登记，展示它被哪些项目／Agent 入口使用 | 修改全局规则时明确影响范围，不偷偷复制到每个仓库 |
| 大项目模块约束 | 可选模块文档，声明适用目录；项目入口提供读取路由 | 小项目只有一个入口；大型项目能按模块看到应读文件 |
| 项目维护日志 | 项目内 Markdown，记录背景、结果、验证和遗留事项 | 换 Agent 后仅凭仓库文档即可理解关键修改缘由 |
| 自动提炼、人工审核 | 当前工作的 Agent 自动提出候选，待审区与生效文件分离 | 未审核候选不会被当成有效规则；拒绝不会改原文 |
| 多项目管理看板 | 显式登记路径，聚合规则、待审提案、日志和可用 Git 历史 | 在一个界面切换项目，看到规则来源与维护轨迹 |

## 3. 文件组织：只有一份正式内容

工作台自己的本机文件，路径可配置：

```text
~/.config/agent-workbench/
  projects.json              # 本机项目路径、现有文档位置、Agent 入口映射
  global/AGENTS.md            # 可选；也可登记已有全局文件，二选一
~/.local/share/agent-workbench/
  proposals/<id>.json         # 尚未生效的候选与审核状态
  receipts/<id>.json          # 应用记录、恢复依据；不保存完整对话
```

被管理的项目只需要自己的文件：

```text
project/
  AGENTS.md                  # 偏好、项目边界、按任务读取的链接
  docs/agent/                # 大型项目可选，现有目录也可直接映射
    backend.md
    frontend.md
  docs/maintenance/
    2026-11.md               # 重要维护背景，按月追加
```

不强制创建空目录、空模块文件或额外 YAML 配置。已有 architecture、decisions、maintenance 文档可以直接登记；同一事实不再生成一份工作台专用副本。项目注册表只保留本机路径与映射，不写入公开仓库。待审提案和个人来源默认也只在本机，分享需显式导出。

已有 mini-trellis 项目继续使用 `.trellis/spec/`、`research/`、`workspace/<name>/journal-*.md`，直接登记原路径，不再生成第二份月度日志。新项目可以采用上面的 docs 组织，无需先运行完整 `mini-trellis init`。目录位置是映射，不是必须遵循的新框架。

项目 AGENTS.md 继续用普通 Markdown，不要求每段加 ID 或 frontmatter。只有可选的独立模块规则需要机器发现时，才采用 CE 的 `title`、`applies_when` 约定，并增加简单的结构校验。证据子目录不是活动规则目录，维护日志也不是默认注入的指令。

全局来源登记不代表任何 Agent 已经加载它。首版先明确记录实际读取入口；适配不同 Agent 时仅生成必要的入口或映射，并预览改动。子模块、独立 Git 仓库以及任意 docs 子目录都不假定会自动继承父规则。

多个作用域出现矛盾时，界面并列展示来源与适用条件，让用户审核明确的局部例外。工作台不靠一个通用“后者覆盖前者”的规则消除语义冲突。

## 4. 生成候选与审核

不新增一个常驻“记忆 Agent”。由正在工作的 code agent 使用当前对话和项目文件：遇到明确纠正、表达长期偏好、同类问题复发或结束重要任务时，自动判断是否有值得保留的候选。用户也可随时要求提炼。若无法获得宿主的对话上下文，则只使用用户或 Agent 主动提供的片段，不承诺后台读取所有历史聊天。

候选应回答：原话或问题是什么；为什么值得长期保留；适用于哪里；现有代码／检查／文档是否已经表达；应该新增、修改、合并还是删除。没有新增信息就不提案。局部习惯默认留在项目；推广到全局是另一份明确审核的提案。

一份提案只改一个文件，核心数据为：

| 数据 | 作用 |
| --- | --- |
| `id`、创建时间、项目／作用域、目标文件 | 定位与影响范围 |
| 原文 SHA-256、候选完整新文本、候选内容 hash | 锁定用户实际审阅的版本，差异从这两版生成 |
| 原因、触发条件、必要来源摘要／引用 | 说明为什么改，避免泄漏完整对话 |
| 状态、审核与应用回执引用 | 跟踪 pending、applied、rejected、conflict |

流程：**自动提炼 → 本机待审 → 查看原文与差异 → 修改／批准／拒绝 → 检查原文是否仍一致 → 原子写入 → 留下回执与维护摘要**。

用户修改候选后必须重新看到最终 diff。批准必须绑定候选内容 hash 和原文 hash；文件被其他 Agent 改过则进入 conflict，重新生成差异后再审，不自动合并后直接应用。新增文件的“原文”是不存在的状态，不能覆盖同时创建的文件。

待审内容不进入规则发现或 Agent 启动注入路径。Agent 可读、提案、通过 change 直接修改并记录已获授权的约束；仍不提供提案自动批准参数。看板写入只接受本机 UI 会话的请求，校验来源与会话令牌。

这是应用工作流的审核保证，不能隔离拥有同一用户文件权限的 code agent。用户直接编辑文件、其他工具越过看板写文件时，应显示“外部修改”，不能伪造为已审核。若以后要求操作系统层面的强制隔离，应单独设计，而非首版引入沙箱系统。

## 5. 写入与恢复保持小而可靠

只处理已登记目标，校验规范化路径和所属目录；首版不经符号链接写入。先保存带前后 hash 的应用意图和必要旧版本，再同目录临时写入、原子替换，最后完成回执和日志。

中断恢复按目标内容核对：仍为原文则允许继续；已是审核版本则补齐回执／日志；两者都不是则标冲突。相同提案重复提交不会重复写入或重复记日志。用户后续编辑优先保留，不自动回滚覆盖。单文件原子替换不等同于目标、回执和日志跨文件原子事务，恢复步骤专门处理这个间隙。

不自动 git add、commit、push、stash 或修改分支。没有 Git 也能使用当前文件、提案回执与维护日志；有 Git 则补充真实提交与文件历史。多文件或跨项目修改拆成可独立审核的提案，不承诺原子批量变更。

## 6. 维护路径怎么呈现

项目内只有约束、提案、维护记录；全局偏好从独立入口维护。没有项目总览页，也不在项目内划分全局／项目／模块标签。

维护记录保留工程决策看板四种视角，默认架构基线：

1. 架构基线：已落地且未归档、未显式被替代的决定，保留关键引用排序与主题分组。
2. 演进时间线：同一批决策按笔记日期和月份排列，不用迭代日志替代决策，不推测实施日期。
3. 避坑智库：已否决方案与其他决定中的真实备选、收益和代价。
4. 决策清单：全部生命周期的紧凑检索表。

四视图从同一批 `.agents/notes` 派生，共用月份、类别、状态、搜索及详情选择；切换视图保留筛选。基线和避坑按用途投影子集，并不要求四页条数相同。基线领域分组包括当前已落地决定与方案稿。桌面和窄屏均使用带遮罩及焦点约束的同页右侧抽屉；内部关联直接替换抽屉内容，支持浏览器前后退。实际迭代保留为“迭代日志”入口及详情中的关联，不作为四视图中的另一套数据。迭代可引用已有决定，不重复其正文。决策实施状态与约束提案审核状态彼此独立。看板决策仅阅读；写作、移动和状态正文由 Agent 维护，CLI 提供格式／链接／封印校验及归档计划执行。

归档使用 `src/notes.mjs`，通过现有 CLI 和 Skill wrapper 访问已登记项目；不新增 HTTP 写接口。只读计划列出前后文本与入站引用，执行时重新核对项目、映射和完整内容。多文件按意图回执恢复，共用工作台数据目录锁；任一目标变成有效约束或出现外部新编辑时停止。归档本身不修复入站链接、不自动留日志、不提交 Git。归档头部、manifest v1、SHA-256 和可选 Git 历史基线与 write-notes 概念兼容，工具为本仓库独立实现，未移植上游源码。跨文件不是原子事务，锁也不能阻止外部文件工具；具体流程与边界由 Skill 参考文件说明。

日志只留关键背景，不记每次工具调用。推荐每条包括日期、为什么改、实际结果、验证／缺失验证、后续事项；提交引用可空。提案批准事件自动留事实摘要；普通任务由工作 Agent 在重要变更结束后维护日志。日志不把未经审核的建议写成有效约束，也不把计划写成已实现行为。

“维护路径”是文档时间线和明确引用，首版不做知识图谱。读取入口默认只载入索引和相关记录，不把多年日志塞进每次会话。

## 7. 运行与代码边界

建议单个 TypeScript／Node 包与一个本机 HTTP 进程，复用 `mini-trellis-core`，浏览器端使用静态 HTML/CSS 与原生模块。使用仍受维护的 Node LTS；实际最低版本在实现构建时确定，上游声明为 Node ≥18.17 不等于本项目继续支持旧版本。Git 是可选能力。既有 mini-trellis workspace 日志只读兼容；新记录写入配置的维护目录，不执行用户仓库中的脚本，也不修改上游 journal 索引。原记录器适配留待有实际需求时再设计。首版不依赖数据库、模型 API、后台队列或桌面壳。

内部只有文件目录与读取、提案审核与应用、维护记录三个职责模块，CLI 与 HTTP 共用它们。若简单 HTTP 实现不足，再按具体问题引入一个小依赖；不为了“零依赖”自行实现复杂网络功能。界面开启时只检查登记的文件，关闭后不要求守护进程。缓存可以删除重建，不承担正式内容。

复用边界：`discoverDocs` 只负责项目文档发现，不等于有效规则列表；全局文件由独立登记来源读取，不能强行穿过其项目边界。`listMemProjects` 按本机会话 cwd 聚合，不作为工作台注册表。`recallMem` 会同时扫描文档和会话，首版浏览规则不直接调用它；需要历史依据时才显式限定来源／会话。若要文档单独召回，优先加一个小的来源过滤扩展，不另建索引服务。新增规则发现、审核和摘要都不能把日志、被否决提案或 superseded 文档当成当前指令。

CloudCLI 适配应等待独立闭环可用后再做。其 `mount/unmount`、`context`、`onContextChange`、`rpc` 可供嵌入入口；先验证能否复用同一个工作台服务，不能悄悄再引入一套数据库和项目状态。适配不复制宿主实现；如需复制，重新核对 AGPL 及额外归属条款。

## 8. 实施顺序与退出条件

| 阶段 | 必要交付 | 进入下一步的证据 |
| --- | --- | --- |
| 设计基线（已完成） | 选型、文件组织、融合边界、研究复核 | 本文与源码证据可审阅；当前实现以 README 为准 |
| 第一段：可读 | 显式登记多个项目、展示三层规则与日志、可用 Git 历史 | 空目录、已有项目、独立子仓库都能正确显示；没有隐式写入 |
| 第二段：可审 | 一文件提案、diff、审核落盘、外部修改冲突、中断恢复 | 未批准不生效；审核版本精确匹配；恢复不会覆盖新编辑 |
| 第三段：能积累 | code agent 的短提案协议与按需触发说明、重要维护留档 | 对话里的纠正自动成为待审候选，批准后可在另一 Agent 中读到；六项需求形成闭环 |
| 可选：宿主入口 | 有实际使用需求才接 CloudCLI 等 | 独立模式不受适配器缺失影响，不增加第二份事实来源 |

前三段合起来才是首个满足六项需求的版本。首版不包括聊天系统、任务编排、多用户权限、向量检索、图数据库、模型评分系统、插件市场或远程规则同步。

## 9. 让脚手架逐步变轻

每次提炼先问“这条信息还需要人写下来吗？”代码能直接说明的实现细节、已有检查能稳定保证的行为，不再写成长提示。优先保留个人偏好、真实边界、难从当前代码恢复的决策原因。

复审候选不仅能新增，也能合并、收窄和删除；临时模型补丁可注明何时不再需要。发现失效时自动提出删改建议，仍由用户审核，不按年龄或置信度静默删除规则。

AGENTS.md 长度增长、重复片段、已有检查覆盖的规则可作提示；不设置自动截断，也不把字符数当质量指标。不按对话次数自动积累条目，不要求每次任务产出新规则。界面可不启动、提炼可关闭、适配器可删除，剩下的文件仍然构成完整的项目交接材料。
